# 09 调试过程与问题排查

> 本篇记录本项目**耗时最长、过程最曲折**的一次故障排查。
> 它没有对应单一的考核指标，但对理解整个系统的行为逻辑至关重要。

## 故障现象

### 初始现象

底盘装好、程序烧录、手柄能正常配对后，进行第一次实车测试，发现：

| 操作 | 预期 | 实际 |
| --- | --- | --- |
| **斜向移动**（↑+→ / ↑+← / ↓+→ / ↓+←） | 四个方向斜行 | ✅ **正常** |
| **前进 / 后退**（↑ / ↓） | 四轮同向转，车前进后退 | ❌ **四个轮子都不动** |
| **左移 / 右移**（← / →） | 两侧反向转，车横移 | ❌ **四个轮子都不动** |

**症状非常明确：2 个轮子出力的动作能做，4 个轮子出力的动作完全不动。**

### 架空复测

把机器人架起来（四轮离地）再试：

| 操作 | 架空状态 |
| --- | --- |
| 斜向移动 | ✅ 两个轮子正常转动 |
| 前进 / 后退 / 左移 / 右移 | ❌ 四个轮子都不转 |

**架空都不转** —— 这一条直接排除了"地面摩擦力太大"和"电源带不动 4 个电机"这类负载相关的假设。因为空载时电机几乎不吃力。

## 排查过程

整个排查历时数天，前后提出并**逐一推翻**了 6 个假设。

### 假设 1：电源带不动 4 个电机

**推理依据**：4 个 TT 马达同时启动，电流可能是 2 个马达的数倍，导致电池电压被拉垮、驱动芯片欠压保护。

**验证方法**：用万用表测量电机电源（VM）电压，对比"静止"与"输出时"。

| 状态 | 测得 VM 电压 | 变化 |
| --- | --- | --- |
| 不按键 | 8.00 V | — |
| **按住 ↑（4 电机被命令转）** | **8.00 V** | **完全没掉** |
| 按住斜行（2 电机实际在转） | 7.33 V | 掉了 0.67V |

**结果**：按 ↑ 时电压纹丝不动 → **没有电流 → 电机根本没有被通电**。

**结论**：❌ **推翻。** 如果真是电源带不动，电压应该明显下跌。

> **这里得到一个关键判据**：直流电机只要有电流就必然产生力矩、必然会转（架空状态无负载）。**电压不掉，说明电机侧没电流**，问题在信号或驱动，不在电源。

### 假设 2：驱动芯片（DRV8833）损坏

**推理依据**：后左 + 后右由同一片 DRV8833 驱动，如果那片坏了，两个后轮就不动。

**验证方法**：检查斜行时是哪两个轮子在转。

**结果**：斜行的左前斜（↑+←）用 FR + RL，右前斜（↑+→）用 FL + RR —— **覆盖了全部 4 个电机和 2 片驱动芯片**。

**结论**：❌ **推翻。** 4 个电机、2 片驱动都在斜行中正常工作过。

### 假设 3：电机损坏

**推理依据**：某个电机坏了，所以四轮驱动时凑不齐。

**结果**：同假设 2 —— 4 个电机都在斜行中出现过并正常转动。

**结论**：❌ **推翻。**

### 假设 4：接线错误 / 虚焊 / 接触不良

**推理依据**：某个通道的杜邦线松动或虚焊。

**验证方法**：做了一组对照实验——拔掉部分电机再测。

| 测试 | 结果 |
| --- | --- |
| 拔掉 1 个电机，剩下的按 ↑ | 剩下的**仍然不转** |
| 拔掉 2 个电机（不论是否同一驱动片） | 剩下的**仍然不转** |

**结论**：❌ **推翻。** 如果只是某一通道接触不良，拔掉其他电机后剩余通道应该能转。而且"拔掉任意两个都不转"说明与通道数量无关。

### 假设 5：nSLEEP / STBY 引脚没拉高

**推理依据**：DRV8833 有 nSLEEP（睡眠）引脚，内部下拉，悬空时芯片进入睡眠、8 路输出全部关断。这是"程序完全正确但电机一动不动"的经典原因。

**验证**：检查硬件——**STBY 已直接接电源正极**。

**结论**：❌ **推翻。**（而且斜行能转，说明芯片显然没有睡眠）

### 假设 6：PWM 通道配置错误（PB4 被 JTAG 占用等）

**推理依据**：STM32F103 的 **PB4 默认是 JTAG 的 NJTRST 引脚**，如果 SWJ 配置没有切换到 SWD-only，PB4 会被 JTAG 控制器占用，无法输出 PWM。而 PB4 正是后左轮的 CH1。

**验证**：检查 CubeMX 配置——`__HAL_AFIO_REMAP_TIM3_PARTIAL()` 已生成，且斜行时后左轮正常工作。

**结论**：❌ **推翻。**（PB4 确实能输出 PWM）

## 根因定位：一次决定性的实测

排除了电源、驱动、电机、接线、睡眠引脚、通道配置之后，剩下的唯一变量是：

> **轮子在两种动作中拿到的 duty 数值不同。**

于是在**架空状态**下做了一次最直接的测试：**同一个电机，逐档降低 duty，看它在哪一档开始不转。**

### 测试方法

```c
/* 绕过斜坡和死区补偿，直接调 motor_set 给纯 duty */
motor_coast_all();
motor_set(MOTOR_FL, duty);      /* duty 依次取 1.00 / 0.80 / 0.60 / 0.40 */
HAL_Delay(3000);
```

### 测试结果

| duty | CCR | 现象 |
| --- | --- | --- |
| **1.00** | 3599 | ✅ **转** |
| 0.80 | 2879 | ✅ 转 |
| **0.60** | **2159** | ❌ **不转** |
| 0.40 | 1439 | ❌ 不转 |

**同一个电机、同一个电源、同一套代码，只改 duty 数值。**

### 根因结论

> **TT 马达 + 塑料减速箱存在明显的静摩擦死区。**
> 占空比低于约 0.7 时，电机产生的力矩不足以克服减速箱的静摩擦，**转子锁死不转**。

### 为什么表现为"斜行能走、直行不走"

回到麦轮逆运动学，看两种动作每个轮子实际拿到的 duty：

| 动作 | 参与轮子数 | 计算过程 | 归一化后每个轮子的 duty |
| --- | --- | --- | --- |
| **斜行**（vx=0.6, vy=0.6） | 2 个 | FL=RR=0.6+0.6=**1.2**，FR=RL=0 | 除以 peak(1.2) → **1.00** |
| **直行**（vx=0.6） | 4 个 | FL=FR=RL=RR=**0.6** | peak=0.6 ≤ 1.0，不归一化 → **0.60** |

**关键点：斜行时因为触发了归一化，单个轮子反而跑满速 1.00；直行时只跑 0.60。**

**这就是整个故障的真相** —— 一个反直觉的结论：**"斜行能走"完全不能说明电源够用或力矩够用，它只说明那 2 个通道的硬件是好的。**

## 解决方案

### 方案设计：死区补偿

在 `motor.c` 中增加 `motor_deadzone_comp()`，把命令区间 `[0, 1]` **线性映射**到 `[MOTOR_DEADZONE, MOTOR_MAP_TOP]`：

```c
static float motor_deadzone_comp(float duty)
{
    if (duty == 0.0f) return 0.0f;          /* 0 就是停，绝不能补偿 */

    float sign = (duty > 0.0f) ? 1.0f : -1.0f;
    float mag  = fabsf(duty);

    /* 线性映射：[0,1] → [0.80, 1.00] */
    mag = MOTOR_DEADZONE + mag * (MOTOR_MAP_TOP - MOTOR_DEADZONE);

    if (mag > MOTOR_DUTY_LIMIT) mag = MOTOR_DUTY_LIMIT;
    return sign * mag;
}
```

映射结果：

| 命令 duty | 补偿后 | CCR | 说明 |
| --- | --- | --- | --- |
| 0.00 | **0.00** | 0 | 松手真的会停 |
| 0.30 | 0.86 | 3095 | |
| **0.60** | **0.92** | **3311** | 原来卡死的值，现在抬出死区 |
| 1.00 | **1.00** | 3599 | 斜行仍然满速 |

### 为什么选线性映射而不是"低于阈值直接抬到阈值"

如果简单地"小于 0.8 的全部改成 0.8"，就变成了**开关式控制** —— 按一点和按到底速度一样，失去调速意义。

线性映射保留了速度比例：斜行（原 1.00）→ 1.00，直行（原 0.60）→ 0.92，仍能分辨快慢。

### 为什么 `duty == 0` 必须单独处理

如果对 0 也做补偿，松手后轮子会拿到 0.80 的占空比，**车会一直缓慢爬行**，永远停不下来。这是极其危险的行为，必须显式排除。

## 第二个坑：`MOTOR_MAP_TOP` 设太小导致整车不动

### 现象

第一版把参数设为：

```c
#define MOTOR_DEADZONE   0.72f
#define MOTOR_MAP_TOP    0.90f      /* 意图：限速以保护硬件 */
```

结果：**连斜行都不动了**，整车四个轮子全部停摆。

### 原因分析

按这个映射，斜行（原 1.00）→ 0.90，直行（原 0.60）→ 0.828。

但实测已知 0.60 不转、1.00 转，死区的上界尚未精确测定。把输出上限压到 0.90 后，直行的 0.828 仍落在死区内，等于把有动作都推到了死区边缘。

### 修正

```c
#define MOTOR_DEADZONE   0.80f
#define MOTOR_MAP_TOP    1.00f      /* 必须能到满速 */
```

**关键教训**：

> `MOTOR_MAP_TOP` **必须保留 1.00**，让输出能够达到已经实测"能转"的那个值。
> 宁可跑快一点，也不要为了"保护硬件"把输出压进死区。

修正后，直行（原 0.60）→ **0.92**，斜行（原 1.00）→ **1.00**，全部动作恢复正常。

## 排查过程中被逐一排除的假设汇总

| # | 假设 | 排除依据 |
| --- | --- | --- |
| 1 | 电源带不动 4 个电机 | 按 ↑ 时 VM 稳定 8V 不掉（无电流）；拔掉 2 个电机后剩下的仍不转 |
| 2 | 驱动芯片损坏 | 斜行覆盖了全部 2 片驱动，均正常工作 |
| 3 | 电机损坏 | 斜行覆盖了全部 4 个电机，均正常转动 |
| 4 | 接线错 / 虚焊 | 拔掉任意 1~2 个电机，剩余通道仍不转，与通道无关 |
| 5 | nSLEEP/STBY 没拉高 | 已直接接电源正极；且斜行能转证明芯片未睡眠 |
| 6 | PWM 通道配置错（PB4 被 JTAG 占） | TIM3 部分重映射已配置，PB4 能输出 PWM |
| 7 | 四轮同时驱动导致电流预算不足 | 把四轮降到 0.30（总负荷 1.2，比斜行的 2.0 更低）**仍然不动** |
| 8 | 机械打架（辊子装反） | **架空也不转**，无地面反力 |
| **✓** | **马达静摩擦死区** | **实测 duty 1.00 转、0.60 不转，同电机同代码只改数值** |

### 关键判据 1：为什么能排除"电流预算不足"

如果真是电流不足，那么**把总负荷降到比"能跑的斜行"更低**就应该好转。但实测降到 0.30（总负荷 1.2 < 斜行 2.0）**毫无改善**，所以瓶颈不在总电流。

### 关键判据 2：为什么能排除机械问题

机械打架（辊子装反互相顶住）需要地面反力才能发生。**架空状态下四个轮子各转各的，不存在打架**，但仍然不转 → 不是机械问题。

## 从这次排查中得到的经验

### 经验 1：万用表测 PWM 电压不可靠

在 20kHz PWM 下，万用表测的是平均值，而且**悬空引脚的读数会被漏电和内部下拉电阻干扰**。排查过程中一度量到四个引脚都是 0.8V（预期应为 2.0V），这个数字既不能证明有输出，也不能证明没输出。

**更可靠的判据是"轮子转不转"** —— 物理现象比电压读数更直接。

### 经验 2："电压不掉"可能是坏消息

直觉上电压稳定 = 供电充足 = 好事。但在电机场景下，**电压完全不掉恰恰说明没有电流、电机没在工作**。这个反直觉的判据后来成为定位故障的关键。

### 经验 3：分层架构让排查快了几倍

因为代码是分层的（`main.c` → `chassis.c` → `motor.c`），可以逐层隔离：

| 层 | 验证方法 | 结果 |
| --- | --- | --- |
| `ps2.c` 手柄解析 | 串口打印 `btn1/btn2` | ✅ 正确 |
| `chassis.c` 运动学 | 用仿真复现四个轮子的 duty | ✅ 正确 |
| `motor.c` PWM 输出 | 直接给 duty 测单个电机 | ❌ **问题在这里** |

**如果代码全部堆在 `main()` 里，这个排查过程会痛苦几倍。**

### 经验 4：归一化会掩盖真实的速度差异

"斜行能走、直行不走"看起来像"四个轮子配合不好"，实际上是**斜行的轮子跑得更快**（归一化的副作用）。**看到反直觉现象时，要回到公式算一遍实际数值。**

### 经验 5：先做最小可复现实验

整个排查最关键的一步，不是任何一个假设的论证，而是那个**最简单的实验**：

> 架空 → 单个电机 → 只改 duty → 看转不转

**这个实验 10 秒就能做完，却直接给出了答案。** 反而是前面几天基于假设的间接推理绕了远路。

**教训：当多个假设都难以验证时，应该设计一个能直接观测目标现象的最小实验，而不是继续在假设层面推理。**

### 经验 6：`MOTOR_MAP_TOP` 不能为了"保护"而压死区

修好之后又因为"想限速保护硬件"把上限压到 0.90，结果整车又不动了。**安全限制必须建立在"知道边界在哪"的基础上**，盲目限幅可能反而破坏功能。

修复后的完整功能测试（架空 + 落地均测试）：

| 动作 | duty（补偿后） | 结果 |
| --- | --- | --- |
| 前进 | 0.92 | ✅ 四轮同向转 |
| 后退 | 0.92 | ✅ 四轮反向转 |

**故障已彻底解决。**
