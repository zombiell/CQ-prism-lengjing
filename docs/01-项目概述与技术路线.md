# 01 项目概述与技术路线

## 项目背景与竞赛目标

CRTC2026（重庆大学机器人训练大赛）的核心形式是**机器人之间的资源争夺**：参赛队自行设计、开发、制作 1~2 台机器人，在限定的空间和时间范围内尽可能多地收集和占有有限的道具资源，最终持有道具得分较多的一方获胜。

场地要素包括**高台、坡道、桥梁、台阶、启动区**，道具为场地中央的**能量单元（白色立方体，1 分）**与**能量核心（黄色立方体，4 分）**。这意味着一个合格的参赛机器人需要同时具备：

1. **全向机动能力** —— 在复杂地形中快速穿行、抢占资源
2. **精准定位能力** —— 把机器人准确开到道具位置
3. **抓取携带能力** —— 把道具拿起并带回

在本阶段（中期考核）中，我们集中攻克的是**第 1 项：全向移动底盘**。这是后续所有功能的地基——没有可靠的底盘，抓取机构再精巧也无法完成任务。

## 机器人总体方案

```
                    ┌─────────────────────────┐
                    │   PS2 无线手柄（2.4G）    │
                    └───────────┬─────────────┘
                                │ 无线
                    ┌───────────▼─────────────┐
                    │   PS2 接收器（6 线）      │
                    └───────────┬─────────────┘
                                │ DATA/CMD/CS/CLK
                    ┌───────────▼─────────────┐
                    │   STM32F103C8T6 @72MHz  │
                    │  ┌───────────────────┐  │
                    │  │ ps2.c   手柄解析   │  │
                    │  │ chassis.c 麦轮解算 │  │
                    │  │ motor.c   PWM 输出 │  │
                    │  └───────────────────┘  │
                    └───────────┬─────────────┘
                                │ 8 路 PWM
                    ┌───────────▼─────────────┐
                    │  DRV8833 双 H 桥 × 2     │
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │  TT 减速马达 × 4         │
                    │  麦克纳姆轮 × 4（X 形）   │
                    └─────────────────────────┘
```

软件采用**分层架构**，每层只关心自己的职责，上层不依赖下层的实现细节：

| 层次 | 文件 | 职责 | 对下层的假设 |
| --- | --- | --- | --- |
| 应用层 | `main.c` | 时间片调度、按键解析、急停决策 | 只调用 `chassis_mecanum()`，不知道麦轮公式 |
| 算法层 | `chassis.c` | 麦轮逆运动学、归一化、四轮降额 | 只调用 `motor_set_ramp()`，不知道 PWM 寄存器 |
| 驱动层 | `motor.c` | 死区补偿、软启动、PWM 写入 | 只调用 `motor_set()`，不知道 DRV8833 接线 |
| 驱动层 | `ps2.c` | 时序模拟、协议解析、数据校验 | 只返回结构体，不知道它会被怎么用 |

**这样分层的好处**：在验证"斜行能走、直行不走"这个故障时，我们可以逐层隔离——先确认 `ps2.c` 解析正确（用串口打印 `btn1`），再确认 `chassis.c` 解算正确（用仿真复现），最后把问题锁定在 `motor.c` 的占空比数值上。**如果代码是一整块写在 `main()` 里，这个排查过程会痛苦几倍。**

## 技术难点与创新点

### 难点一：PS2 协议没有现成驱动可用

PS2 手柄使用的是索尼游戏机的私有同步串行协议，非标准 SPI。时钟完全由主机发出，数据在时钟下降沿同步，LSB 先行，半周期约 16µs。

**我们的做法**：用普通 GPIO 软件模拟时序，并用 TIM1 制作 1MHz 计数器实现精确微秒延时。

**为什么不用硬件 SPI / 不用 DWT**：见 [04](./04-PS2手柄通信与遥控.md) 的"技术选型对比"一节。

### 难点二：麦克纳姆轮的"归一化"必须做对

麦轮逆运动学解出四个轮速后，某些动作（如斜行）会让某个轮子超过 100% 的占空比。若简单截断，四个轮子的**相对比例会被破坏**，机器人会走偏而不是走斜。

**我们的做法**：找出四个值中的最大绝对值 `peak`，四个一起除以它。这样最大的一路正好满速，其余按比例缩放，**合成方向完全不变**。

### 难点三（最大的坑）：TT 马达的静摩擦死区

这是本项目耗时最长的故障。现象是**斜行能走、直行不走**，而且所有常规排查（电源、驱动、电机、接线）都指向"没问题"。

**根因**：TT 马达配塑料减速箱，静摩擦较大。占空比 0.60 时电机产生的力矩不足以克服静摩擦，转子锁死不转；而斜行因为归一化的关系，每个轮子反而跑满速 1.00，所以能转。

**解决**：在 `motor.c` 中实现**死区补偿算法**，把命令区间 `[0,1]` 线性映射到 `[0.80, 1.00]`，保证任何非零命令都能真正驱动电机。

**完整排查过程**见 [09-调试过程与问题排查](./09-调试过程与问题排查.md)。

> **这个故障给我们的最大启示**：嵌入式调试中，"电压正常"不等于"电机在工作"。用万用表测 20kHz PWM 的平均电压是不可靠的，而"轮子转不转"才是最直接的判据。
